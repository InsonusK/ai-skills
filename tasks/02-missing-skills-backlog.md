# Бэклог недостающих скиллов

Каждый пункт — это **конкретный скилл**, который нужно доописать. В отличие от поверхностного списка «Бизнес-анализ, Тех-анализ», здесь расписаны:
- какую задачу агент решает с помощью скилла;
- что агент должен сделать;
- входные и выходные данные;
- приоритет.

## Легенда приоритетов

- **P0** — блокирует полноценный end-to-end процесс, делать в первую очередь.
- **P1** — сильно повышает качество и предсказуемость, делать во вторую очередь.
- **P2** — улучшения и специализированные сценарии.

## Этап 1. Прием и фиксация бизнес-требований

### 1.1 `requirement-intake` (P0)
**Задача агента:** правильно принять и классифицировать требование от пользователя.

**Что агент должен делать:**
- Определить тип задачи: новая фича, баг, tech debt, исследование (spike), рефакторинг.
- Для каждого типа задать минимальный обязательный набор вопросов.
- Зафиксировать источник требования и контекст.
- Понять, есть ли уже готовое описание или его нужно выяснить.

**Входные данные:**
- Сообщение пользователя с описанием задачи.
- Контекст проекта (домен, стек).

**Выходные данные:**
- Тип задачи.
- Список полученных фактов.
- Список вопросов, на которые еще нужен ответ.

---

### 1.2 `business-problem-statement` (P0)
**Задача агента:** сформулировать бизнес-проблему в понятном, проверяемом виде.

**Что агент должен делать:**
- Выделить: что не так, для кого это проблема, почему это важно, какой эффект ожидается.
- Перевести размытые формулировки в конкретные утверждения.
- Согласовать формулировку с пользователем, если она неясная.

**Входные данные:**
- Описание задачи от пользователя.
- Контекст бизнес-домена.

**Выходные данные:**
- Business problem statement (1–3 предложения).
- Список предположений, которые нужно подтвердить.

---

### 1.3 `scope-boundary-definition` (P0)
**Задача агента:** четко определить, что входит в задачу, а что — нет.

**Что агент должен делать:**
- Описать in-scope: функциональность, системы, модули, которые затрагиваются.
- Описать out-of-scope: что точно не будет сделано, но может показаться связанным.
- Зафиксировать смежные системы и границы ответственности.

**Входные данные:**
- Business problem statement.
- Описание задачи.

**Выходные данные:**
- In-scope list.
- Out-of-scope list.
- Список смежных систем.

---

### 1.4 `acceptance-criteria-definition` (P0)
**Задача агента:** сформулировать проверяемые критерии приемки.

**Что агент должен делать:**
- Перевести требования в формат Given-When-Then или в список проверяемых условий.
- Для каждого критерия указать: входные данные, действие, ожидаемый результат.
- Убедиться, что критерии покрывают happy path и основные ошибочные сценарии.

**Входные данные:**
- Business problem statement.
- Scope boundaries.

**Выходные данные:**
- Список acceptance criteria.
- Связь каждого критерия с бизнес-требованием.

---

### 1.5 `definition-of-ready-check` (P0)
**Задача агента:** проверить, можно ли начинать разработку.

**Что агент должен делать:**
- Проверить наличие: цели, scope, acceptance criteria, технического контекста, зависимостей.
- Определить, достаточно ли информации для декомпозиции и оценки.
- Если DoR не выполнен — сформулировать, чего не хватает, и задать вопросы пользователю.

**Входные данные:**
- Результаты предыдущих скиллов.

**Выходные данные:**
- DoR checklist с отметками.
- Список блокеров и вопросов.

## Этап 2. Доменный и технический анализ

### 2.1 `domain-event-storming-lite` (P0)
**Задача агента:** выделить доменные события, команды и акторов.

**Что агент должен делать:**
- На основе business problem и acceptance criteria выделить события: "что произошло".
- Для каждого события определить команду: "что вызвало событие".
- Определить акторов (пользователей, внешние системы).
- Построить упрощенную временную диаграмму.

**Входные данные:**
- Business problem statement.
- Acceptance criteria.

**Выходные данные:**
- Список доменных событий.
- Список команд.
- Список акторов.
- Временная диаграмма (mermaid).

---

### 2.2 `aggregate-entity-vo-modeling` (P0)
**Задача агента:** построить доменную модель: агрегаты, сущности, value objects.

**Что агент должен делать:**
- Выделить агрегаты и их корни.
- Определить сущности внутри агрегатов.
- Определить value objects.
- Зафиксировать инварианты и бизнес-правила.
- Применять таксономию: internal/external, mutable/immutable, если это .NET plateau.

**Входные данные:**
- Доменные события и команды.
- Существующая доменная модель (если есть).

**Выходные данные:**
- Список агрегатов, сущностей, value objects.
- Описание инвариантов.
- Схема связей.

---

### 2.3 `business-process-modeling` (P1)
**Задача агента:** смоделировать бизнес-процесс со состояниями и переходами.

**Что агент должен делать:**
- Описать happy path.
- Описать альтернативные пути и ошибочные сценарии.
- Зафиксировать состояния и переходы (state machine).
- Указать точки принятия решений.

**Входные данные:**
- Acceptance criteria.
- Доменные события.

**Выходные данные:**
- Диаграмма состояний/переходов (mermaid).
- Описание каждого шага.

---

### 2.4 `api-contract-design` (P0)
**Задача агента:** спроектировать контракты API.

**Что агент должен делать:**
- Определить endpoints/operations.
- Описать request/response DTO.
- Описать коды ошибок и problem details.
- Учесть версионирование и breaking changes.
- Согласовать контракт с существующими соглашениями проекта.

**Входные данные:**
- Агрегаты и команды/запросы.
- Существующие API проекта.

**Выходные данные:**
- OpenAPI/Swagger-like описание.
- DTO с полями и валидацией.
- Ошибки и коды.

---

### 2.5 `database-schema-design` (P0)
**Задача агента:** спроектировать схему реляционной БД.

**Что агент должен делать:**
- Определить таблицы и их назначение.
- Описать колонки, типы, nullable, дефолты.
- Описать связи: PK, FK, 1:1, 1:N, M:N.
- Определить индексы для производительности.
- Учесть мягкое удаление, если принято в проекте.

**Входные данные:**
- Доменная модель.
- Требования к производительности.

**Выходные данные:**
- ER-диаграмма или табличное описание схемы.
- Описание индексов.

---

### 2.6 `ef-core-migrations-design` (P1)
**Задача агента:** корректно спроектировать и применить миграции EF Core.

**Что агент должен делать:**
- Определить, нужна ли новая миграция или изменения в существующей.
- Проверить безопасность миграции для production (добавление nullable, переименования, удаление).
- Использовать `Ensure`/`Up`/`Down` корректно.
- Добавить seed-данные при необходимости.

**Входные данные:**
- Схема БД.
- Существующие миграции.

**Выходные данные:**
- План миграций.
- Команды для генерации и применения.

---

### 2.7 `integration-design` (P1)
**Задача агента:** спроектировать интеграции с внешними системами.

**Что агент должен делать:**
- Выбрать тип интеграции: sync REST/gRPC, async messaging, file exchange.
- Определить idempotency key и retry policy.
- Спроектировать outbox / inbox при необходимости.
- Описать обработку ошибок и dead letter.
- Спроектировать контракты сообщений.

**Входные данные:**
- Требования к интеграции.
- Существующие интеграции в проекте.

**Выходные данные:**
- Схема интеграции.
- Контракты сообщений.
- Политика retry/idempotency.

---

### 2.8 `risk-assessment` (P1)
**Задача агента:** оценить технические и бизнес-риски задачи.

**Что агент должен делать:**
- Выделить технические риски: производительность, сложность, зависимости, breaking changes.
- Выделить бизнес-риски: ошибки в расчетах, доступность, соответствие законодательству.
- Оценить влияние и вероятность.
- Предложить митигацию.

**Входные данные:**
- Весь контекст задачи.

**Выходные данные:**
- Risk register.
- План митигации.

---

### 2.9 `adr-authoring` (P1)
**Задача агента:** зафиксировать архитектурные решения в ADR.

**Что агент должен делать:**
- Определить, требуется ли ADR.
- Сформулировать контекст, решение, последствия, альтернативы.
- Оформить ADR в согласованном формате проекта.

**Входные данные:**
- Архитектурное решение.

**Выходные данные:**
- Файл ADR в `docs/adr/` или аналогичном месте.

## Этап 3. Планирование реализации и тестирования

### 3.1 `implementation-planning` (P0)
**Задача агента:** составить пошаговый план реализации.

**Что агент должен делать:**
- Декомпозировать задачу на атомарные шаги.
- Определить порядок и зависимости.
- Для каждого шага указать: что делаем, какой артефакт получаем, как проверяем.
- Использовать формат implementation plan проекта.

**Входные данные:**
- Результаты анализа.
- Выбранные solution-скиллы.

**Выходные данные:**
- Implementation plan (markdown).

---

### 3.2 `solution-selection` (P0)
**Задача агента:** выбрать подходящие архитектурные solution-скиллы для задачи.

**Что агент должен делать:**
- Просканировать существующие solution-скиллы.
- Сопоставить задачу с паттернами.
- Выбрать минимальный необходимый набор скиллов.
- Объяснить, почему выбран именно этот набор.

**Входные данные:**
- Implementation plan.
- Каталог solution-скиллов.

**Выходные данные:**
- Список применяемых solution-скиллов.
- Обоснование выбора.

---

### 3.3 `relative-estimation` (P2)
**Задача агента:** дать относительную оценку сложности задачи.

**Что агент должен делать:**
- Разбить задачу на подзадачи.
- Оценить каждую как S/M/L или story points.
- Учесть неопределенность и риски.
- Не давать абсолютных часов без запроса.

**Входные данные:**
- Implementation plan.

**Выходные данные:**
- Оценка по подзадачам.
- Обоснование.

---

### 3.4 `test-planning` (P1)
**Задача агента:** составить план тестирования.

**Что агент должен делать:**
- Определить уровни тестов: unit, integration, e2e, manual.
- Для каждого acceptance criterion выделить тестовые сценарии.
- Определить edge cases и негативные сценарии.
- Спланировать тестовые данные.

**Входные данные:**
- Acceptance criteria.
- Implementation plan.

**Выходные данные:**
- Test plan.

---

### 3.5 `definition-of-done` (P1)
**Задача агента:** определить, когда задачу можно считать выполненной.

**Что агент должен делать:**
- Сформулировать DoD: код, тесты, покрытие, review, CI, документация.
- Учесть проектные стандарты.
- Получить согласие пользователя.

**Входные данные:**
- Implementation plan.
- Test plan.

**Выходные данные:**
- DoD checklist.

**Выходные данные:**
