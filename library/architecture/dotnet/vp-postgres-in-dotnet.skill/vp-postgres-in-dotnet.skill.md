# Goal
- **The PostgreSQL variation point in dotnet** - A dotnet application that keeps every property of [vp-postgres](library/architecture/spec/vp-postgres.skill/vp-postgres.skill.md) in its entities form; this skill details its implementation for dotnet and restates none of its rules.
- **Attached by the listed changes only** - Attaching it to [vp-http-api-in-dotnet](library/architecture/dotnet/vp-http-api-in-dotnet.skill/vp-http-api-in-dotnet.skill.md)'s proto example, whose sample handlers keep the lists in the process, changes only the files [attach.allow](./attach.allow) names: the composition root, the build files, and that sample code, which takes the repository; the item gets its key and its list, and its table is configured in its module. The repository's attach check verifies it.

# Core Principle
- **EF Core maps the domain, the module owns its tables** - An entity of `{Module}.Domain` is a row of its table, configured in `{Module}.Domain/Configurations`; `AppDbContext` applies each module's configurations; no row class stands between the domain and its tables. Decision recorded in [entities-mapped-by-ef-core](./adr/entities-mapped-by-ef-core.md).
- **The handler takes Ardalis's repository** - `IRepository<T>` of `Shared.Persistence` over `PostgresRepository<T> : RepositoryBase<T>`, one for every entity; specifications are Ardalis's, in `{Module}.Application/Specifications`. Decision recorded in [repository-over-ardalis-specifications](./adr/repository-over-ardalis-specifications.md).
- **One middleware tells the failures** - `StoreFailuresMiddleware` turns PostgreSQL's failures into error kinds for every command. Decision recorded in [failures-told-by-a-command-middleware](./adr/failures-told-by-a-command-middleware.md).
- **A write saves at once** - So a failure reaches the handler at its write. Decision recorded in [a-store-saves-at-once](./adr/a-store-saves-at-once.md).
- **The context tracks one command** - A loaded entity saves what changed; a failed save clears the tracker. Decision recorded in [the-context-tracks-one-command](./adr/the-context-tracks-one-command.md).
- **One scope per command** - `ScopedSender` gives a command and its nested commands one context. Decision recorded in [one-scope-per-command](./adr/one-scope-per-command.md).

```
src/
├── Shared.Persistence/                         copied: IRepository, SpecificationPage, IStoreFailures, the project
├── Middleware/StoreFailures/                   copied: StoreFailuresMiddleware<,>
├── BuildingBlocks/Pipeline/ScopedSender.cs     copied: AddCommandScope, one scope per command
├── App/App.Migrate/                            copied: the job, /app/migrate of the image
├── Modules/{Module}/
│   ├── {Module}.Domain/Entities/{Entity}.cs    per table: the entity, a row of it
│   ├── {Module}.Domain/Configurations/{Entity}Configuration.cs   per table: its mapping
│   └── {Module}.Application/Specifications/{Name}.cs   per set of rows a handler picks
└── Infrastructure/Postgres/
    ├── Postgres/
    │   ├── Postgres.csproj                     references every {Module}.Domain that keeps data
    │   ├── AppDbContext.cs                     one line per module: its configurations
    │   ├── AppDbContextFactory.cs, PostgresConfig.cs, PostgresModule.cs,
    │   │   PostgresMigrations.cs, PostgresFailures.cs     copied
    │   ├── Repositories/PostgresRepository.cs  copied
    │   └── Migrations/                         generated: make migration NAME=...
    ├── Postgres.Testing/                       copied: TestDatabase, InMemoryRepository
    └── Postgres.Tests/                         features/ holds the copies of the shared scenarios
```

# Rule

## MUST

### Copy the fixed code from templates
Copy [templates/src](./templates/src/), with `dotnet-tools.json` of the example to `.config/`, add the projects to the solution, the package versions of the example's `Directory.Packages.props` (`Microsoft.Extensions.*` raised to EF Core's version, EF Core pinned), and the Makefile targets `migrate` and `migration`; write `Postgres.csproj` and `AppDbContext.cs` as the example's, with a `ProjectReference` and an `ApplyConfigurationsFromAssembly` line for each module that keeps data.
- Violation: a second `DbContext` per module; a `DbSet` property edited into `AppDbContext`; `App.Host` referencing `Postgres` from anything but `Program.cs`; a handler referencing `Postgres`.
- Risk: two contexts mean two migration histories over one database; a handler over `AppDbContext` cannot run over the repository in memory of its scenarios.
- Fix: a table adds its entity, its configuration, its specifications, and its migration in its module; a new module adds its line to `AppDbContext`.

### Register the database, the command scope, and the failures middleware
Load `PostgresConfig.Load()` in the `try` of `AppConfig.Load()`, call `AddPostgres` in `// [services]`, which registers `IRepository<>` and `IReadRepository<>` for every entity, call `AddCommandScope()` after every `Add{Module}Module()`, list `StoreFailuresMiddleware<,>` right after `LoggingMiddleware<,>`, and turn `ValidateScopes` on.

```csharp
// src/App/App.Host/Program.cs, RunAsync
AppConfig config;
PostgresConfig postgres;
try
{
    config = AppConfig.Load();
    postgres = PostgresConfig.Load();   // names the variable, never the DSN
}
catch (FormatException configError)
{
    using var bootLogging = LoggerFactory.Create(logging => logging.AddProvider(new JsonLogProvider(stderr)));
    bootLogging.CreateLogger("App.Host").Write(LogLevel.Error, "startup failed", configError);
    return EntryRunner.ExitFailure;
}

// [services]
services.AddPostgres(postgres);   // IRepository<> and IReadRepository<> of every entity

// [handlers]
services.AddTodoModule();
services.AddCommandScope();       // after every Add{Module}Module
services.AddCommandMiddleware(
    typeof(LoggingMiddleware<,>),
    typeof(StoreFailuresMiddleware<,>));

// after the entries, before they run
await using var provider = services.BuildServiceProvider(new ServiceProviderOptions { ValidateScopes = true });
var logger = provider.GetRequiredService<ILoggerFactory>().CreateLogger("App.Host");
if (postgres.MigrateOnStart)
{
    try
    {
        await PostgresMigrations.ApplyAsync(postgres, stopping);
    }
    catch (Exception migrationError)
    {
        logger.Write(LogLevel.Error, "startup failed", migrationError);
        return EntryRunner.ExitFailure;
    }
}
```

- Violation: `StoreFailuresMiddleware` before the logging or after the unit of work; `AddSingleton` of a type over a repository; an entry point resolving `IMediator`; a handler running nested commands with `Task.WhenAll`.
- Risk: the log misses the kind or the cause, or a failed commit reaches the caller with no kind; a singleton keeps one context for every command; `IMediator` from the root skips the scope; a context serves one call at a time.
- Fix: everything over the context is scoped; entries and handlers take `ISender`; nested commands run one after another.

### Map each entity in its module
Write one `IEntityTypeConfiguration<TEntity>` per table in `{Module}.Domain/Configurations/`, naming the table, columns, and indexes in snake_case explicitly, with a unique index for every rule of uniqueness, and add the module's line to `AppDbContext`.

```csharp
// src/Modules/Todo/Todo.Domain/Configurations/ItemConfiguration.cs
item.ToTable("list_items");
item.HasKey(entity => entity.Id);
item.Property(entity => entity.ListId).HasColumnName("list_id");
item.HasIndex(entity => new { entity.ListId, entity.Title }).IsUnique().HasDatabaseName("list_items_list_id_title_key");

// src/Infrastructure/Postgres/Postgres/AppDbContext.cs, OnModelCreating
// [modules] - one line per module that keeps data.
modelBuilder.ApplyConfigurationsFromAssembly(typeof(ItemConfiguration).Assembly);
```

- Violation: a `[Table]` attribute; a provider package (Npgsql) or a `DbContext` in `{Module}.Domain`; the configuration of a module's table in the Postgres project; a rule of uniqueness checked in the handler with no index behind it.
- Risk: the domain opens connections; a module that adds a table edits the store's project; two concurrent commands both pass a check that has no index behind it.
- Fix: `{Module}.Domain` references EF Core's relational model API (`Microsoft.EntityFrameworkCore.Relational`) for its configurations, no provider; the index holds the rule under a race and the middleware answers it; an entity keeps a constructor whose parameters name its properties, and a key EF Core can set (a private setter); a table of no module (an outbox, a cache of another system's data) is configured in the Postgres project.

### Write a specification per set of rows
Derive from `Specification<TEntity>` in `{Module}.Application/Specifications/`, adding `ISingleResultSpecification<TEntity>` for a key, with its order and page when a list needs them.

```csharp
// src/Modules/Todo/Todo.Application/Specifications/ItemsOfList.cs
public sealed class ItemsOfList : Specification<Item>
{
    public ItemsOfList(string listId) => Query.Where(item => item.ListId == listId).OrderBy(item => item.Id);
}
```

- Violation: a specification with `Skip` or `Take` given to `CountAsync`, `AnyAsync`, or `DeleteRangeAsync`; a condition inlined in a handler; a specification in the Domain or the Postgres project.
- Risk: a count or a delete applies the conditions and ignores the page, so it works on other rows than the list beside it; the domain, which holds the entities and their rules, takes a package of queries.
- Fix: `PostgresRepository` and `InMemoryRepository` refuse a page there (`SpecificationPage`); a page is one specification, the count of the same rows another.

### Pick, change, and save in the handler
Take `IRepository<TEntity>` in a handler that writes and `IReadRepository<TEntity>` in one that only reads, pick the entities by a specification, call their methods, and save them with `AddAsync` or `UpdateAsync`.

```csharp
// src/Modules/Todo/Todo.Application/Commands/AddItemHandler.cs
var item = Item.InList(command.ListId, command.Title);
if (await items.AnyAsync(new ItemOfListTitled(command.ListId, item.Title), cancellationToken))
{
    throw TodoErrors.ItemAlreadyInList(command.ListId, item.Title);   // the rule's own message
}
await items.AddAsync(item, cancellationToken);   // under a race the index answers: conflict
```

- Violation: a handler catching `DbUpdateException` or reading a `PostgresException`; a service between a handler and its own database.
- Risk: the engine's codes leak into the application.
- Fix: the handler states its rules before the write; the middleware tells the failures; a service stays for another system's API. The handler's scenarios run over `InMemoryRepository<T>` of `Postgres.Testing`, with no database.

### Pass a statement of its own through the base class
Derive `{Entity}Repository : PostgresRepository<TEntity>` with an interface extending `IRepository<TEntity>`, and run a statement past SaveChanges in `WriteAsync`.

```csharp
public Task<int> RenameAsync(string from, string to, CancellationToken cancellationToken) =>
    WriteAsync(
        () => Context.Set<OwnerTask>().Where(task => task.Title == from).ExecuteUpdateAsync(task => task.SetProperty(entity => entity.Title, to), cancellationToken),
        cancellationToken);
```

- Violation: `ExecuteUpdate`, `ExecuteDelete`, or raw SQL called past `WriteAsync`.
- Risk: the rules of [vp-postgres](library/architecture/spec/vp-postgres.skill/vp-postgres.skill.md#go-past-the-contract-with-a-method-of-its-own) break: outside the unit of work's transaction, the statement stays after a rollback, and a failure in it breaks an open transaction.
- Fix: register the derived repository `Scoped` in `// [services]` under its own interface; [statements.feature](./examples/src/Infrastructure/Postgres/Postgres.Tests/features/statements.feature), a shared scenario, runs two such statements.

### Generate every migration
Change the entity or its configuration, run `make migration NAME={What}`, read what it wrote, and commit it with the change; apply with `make migrate` locally and with `App.Migrate` in a deployment, publishing it beside `App.Host` so the image has `/app/migrate`.
- Violation: a `HasPendingModelChanges` scenario removed; a migration edited after it was applied somewhere; `EnsureCreated` in the application.
- Risk: the model and the schema drift, and `MigrateAsync` stops the deployment; `EnsureCreated` leaves no history.
- Fix: a new migration for every further change. Decision recorded in [migration-job-as-a-project](./adr/migration-job-as-a-project.md).

### Register the readiness check
`AddPostgres` registers the check of `AspNetCore.HealthChecks.NpgSql` under the name `database` in the framework's registry, the same in every application, whether or not it has a health entry point.

```csharp
services.AddHealthChecks().AddNpgSql(config.Dsn, name: "database");
```

- Violation: a readiness check that sends a command; a `using` of `Api/Management` in the Postgres project; a line for the check in `Program.cs`.
- Risk: a check through a command fails on a business rule and holds traffic back for nothing; a type of the health entry point here stops the project building without it.
- Fix: the check opens a connection of its own, and [vp-health-in-dotnet](library/architecture/dotnet/vp-health-in-dotnet.skill/vp-health-in-dotnet.skill.md) reads the registry; with no health entry point nothing runs the check. `Postgres.Tests` takes the check from the registry by its name and runs it on a database that answers and on one that does not.

### Run the shared scenarios
Name the shared scenarios of `vp-postgres`'s `conformance/` in [conformance.copy](./conformance.copy), run `make conformance-sync`, and implement their steps in `Postgres.Tests/Steps` over `PostgresRepository<T>`, an outcome being what `PostgresFailures` tells of the failure.
- Violation: a copy edited; `conformance/postgres-selector/` copied, whose selector this form does not have.
- Risk: the contract is proved in another stack and not in this one.
- Fix: the sample entities and their specifications are in `Steps/SampleTables.cs`, created by `EnsureCreated` for the scenario; what only dotnet has stays beside the copies, named `{name}-in-dotnet.feature`: `config-forms-in-dotnet`, `model-changes-in-dotnet`, `pages-in-dotnet`, `list-items-in-dotnet` (the example's items kept and read), and `in-memory-repository-in-dotnet` (the repository of the handlers' scenarios).

### Create the database of each scenario
Create a `TestDatabase` per scenario, apply `PostgresMigrations.ApplyAsync` where the scenario needs the schema, and dispose it after the scenario.
- Violation: `TestDatabase` in a static field; `DisableTestParallelization` removed from a project whose scenarios set the environment.
- Risk: scenarios see each other's rows.
- Fix: the database is created in a step and dropped in `[AfterScenario]`; the DSN of `TEST_DATABASE_DSN` needs `CREATEDB`.

# Check list
- [ ] The fixed files are unchanged copies of the templates; one `AppDbContext`, one migration history.
- [ ] `AddPostgres` registers the repositories; every handler over the database's data takes `IRepository<T>` or `IReadRepository<T>`.
- [ ] `StoreFailuresMiddleware` follows `LoggingMiddleware`; no handler reads a failure of EF Core or Npgsql.
- [ ] Every table has one configuration, in its module's Domain; `AppDbContext` has a line per module; no provider is referenced by a Domain project.
- [ ] Repositories and the types over them are scoped; `AddCommandScope()` follows every module; `ValidateScopes` is on.
- [ ] A specification with a page serves a list only; specifications live in the module's Application.
- [ ] A statement past SaveChanges runs in `WriteAsync`.
- [ ] Every uniqueness rule has a unique index; names are snake_case.
- [ ] Every change of the mapping has its generated migration; the scenario on `HasPendingModelChanges` passes.
- [ ] `App.Migrate` is published as `/app/migrate`; `MIGRATE_ON_START` stays `false` beyond one instance.
- [ ] `make test` passes with `TEST_DATABASE_DSN` set; `bash test/check-vp-attach.sh` in this repository reports no file changed beyond [attach.allow](./attach.allow); `bash test/check-conformance.sh` reports no copy changed.
