# Goal
- **The PostgreSQL variation point in dotnet** - A dotnet application that keeps every property of [vp-postgres](library/architecture/spec/vp-postgres.skill/vp-postgres.skill.md); this skill details its implementation for dotnet and restates none of its rules.
- **Attached by the listed changes only** - Attaching it replaces the in-memory store of [vp-http-api-in-dotnet](library/architecture/dotnet/vp-http-api-in-dotnet.skill/vp-http-api-in-dotnet.skill.md)'s proto example and changes only the files [attach.allow](./attach.allow) names, which the repository's attach check verifies.

# Core Principle
- **EF Core behind one generic repository** - One `AppDbContext`, a row class per table, `PostgresRepository<TRow>` for all of them; specifications are Ardalis's, the repository and its selectors are ours. Decision recorded in [repository-over-ardalis-specifications](./adr/repository-over-ardalis-specifications.md).
- **A repository calls SaveChangesAsync** - So the duplicate key reaches the service. Decision recorded in [a-store-saves-at-once](./adr/a-store-saves-at-once.md).
- **The context holds nothing between calls** - Reads track nothing and every save empties the tracker. Decision recorded in [the-context-holds-nothing-between-calls](./adr/the-context-holds-nothing-between-calls.md).
- **One scope per command** - `ScopedSender` gives a command and its nested commands one context. Decision recorded in [one-scope-per-command](./adr/one-scope-per-command.md).

```
src/
├── BuildingBlocks/Pipeline/ScopedSender.cs     copied: AddCommandScope, one scope per command
├── App/App.Migrate/                            copied: the job, /app/migrate of the image
└── Infrastructure/Postgres/
    ├── Postgres.Abstractions/
    │   ├── IRepository.cs, ISelectors.cs       copied: the contract
    │   ├── StoreExceptions.cs                  copied: the outcomes
    │   ├── Rows/{Thing}Row.cs                  per table: the row
    │   └── Specifications/{Name}.cs            per set of rows
    ├── Postgres/
    │   ├── AppDbContext.cs, AppDbContextFactory.cs, PostgresConfig.cs, PostgresModule.cs,
    │   │   PostgresMigrations.cs, StoreFailures.cs     copied
    │   ├── Repositories/                       copied: PostgresStatements, PostgresRepository, Selectors
    │   ├── Rows/{Thing}RowConfiguration.cs     per table: the mapping
    │   └── Migrations/                         generated: make migration NAME=...
    ├── Postgres.Testing/                       copied: TestDatabase, InMemoryRepository
    └── Postgres.Tests/                         features/ holds the copies of the shared scenarios
```

# Rule

## MUST

### Copy the fixed code from templates
Copy [templates/src](./templates/src/), with `dotnet-tools.json` of the example to `.config/`, add the projects to the solution, the package versions of the example's `Directory.Packages.props` (`Microsoft.Extensions.*` raised to EF Core's version, EF Core pinned), and the Makefile targets `migrate` and `migration`.
- Violation: a second `DbContext` per module; a `DbSet` property edited into `AppDbContext`; `App.Host` referencing `Postgres` from anything but `Program.cs`.
- Risk: two contexts mean two migration histories over one database; a retyped `StoreFailures` reads an error code in several places.
- Fix: a table adds its row, its configuration, its specifications, and its migration; no fixed file changes.

### Register the database and the command scope
Load `PostgresConfig.Load()` in the `try` of `AppConfig.Load()`, call `AddPostgres` in `// [services]`, which registers `IRepository<>` for every row, call `AddCommandScope()` after every `Add{Module}Module()`, register each service over a repository `Scoped`, and turn `ValidateScopes` on.

```csharp
// [services]
services.AddPostgres(postgres);

// [handlers]
services.AddTodoModule();          // .AddScoped<IItemLists, ItemListsService>()
services.AddCommandScope();

// before the entries
await using var provider = services.BuildServiceProvider(new ServiceProviderOptions { ValidateScopes = true });
if (postgres.MigrateOnStart) { await PostgresMigrations.ApplyAsync(postgres, stopping); } // in a try: a failure logs "startup failed", exit 1
```

- Violation: `AddSingleton<IItemLists, ItemListsService>` over a scoped repository; an entry point resolving `IMediator`; a handler running nested commands with `Task.WhenAll`.
- Risk: a singleton keeps one context for every command, which fails under the first concurrent calls; `IMediator` from the root skips the scope; a context serves one call at a time.
- Fix: everything over the context is scoped; entries and handlers take `ISender`; nested commands run one after another.

### Write a row and its configuration per table
Declare a `{Thing}Row` class in `Postgres.Abstractions/Rows/` and its `IEntityTypeConfiguration` in `Postgres/Rows/`, naming the table, columns, and indexes in snake_case explicitly, with a unique index for every rule of uniqueness.

```csharp
row.ToTable("list_items");
row.Property(item => item.ListId).HasColumnName("list_id");
row.HasIndex(item => new { item.ListId, item.Title }).IsUnique().HasDatabaseName("list_items_list_id_title_key");
```

- Violation: a domain entity mapped; a `[Table]` attribute; uniqueness checked with a select before the insert only.
- Risk: the domain depends on EF Core; two concurrent inserts both pass a check that has no index behind it.
- Fix: the index is the rule; the repository reports its violation.

### Write a specification per set of rows
Derive from `Specification<TRow>` in `Postgres.Abstractions/Specifications/`, or from `Specification<TRow, TResult>` for a projection, and use only `Where`, `Include`, and `Select`.

```csharp
public sealed class ItemsOfList : Specification<ItemRow>
{
    public ItemsOfList(string listId) => Query.Where(item => item.ListId == listId);
}
```

- Violation: `Query.OrderBy`, `Query.Skip`, or `Query.Take`, which `SelectBy` refuses; a projection by a constructor, `new Result(row.Owner.Name)`, that is then ordered.
- Risk: EF Core cannot order by a value it passed to a constructor, and the query fails at run time.
- Fix: a condition across tables follows a navigation property; a projection's type has `required ... { get; init; }` properties, filled by an object initializer.

### Use the repository from the service
Inject `IRepository<TRow>`, ask `SelectBy` for a selector, and turn its outcomes into kinds as [vp-postgres](library/architecture/spec/vp-postgres.skill/vp-postgres.skill.md#report-a-repositorys-outcomes-in-its-own-terms) requires.

```csharp
var items = await rows.SelectBy(new ItemsOfList(listId)).OrderBy(row => row.Id).AllAsync(cancellationToken);
```

- Violation: `AppDbContext` in a service; a repository returning `IQueryable`; a failed save caught to retry on the same row object with no new read.
- Risk: a query built above the repository depends on EF Core.
- Fix: the service sees `Postgres.Abstractions` only; its scenarios take `InMemoryRepository<TRow>` of `Postgres.Testing` and set its `Failure`.

### Pass a statement of its own through the base class
Derive `{Thing}Repository : PostgresRepository<TRow>` with an interface extending `IRepository<TRow>`, and run a statement past the contract in `WriteAsync`, or a read in `ReadAsync`.

```csharp
public Task<int> RenameAsync(string from, string to, CancellationToken cancellationToken) =>
    WriteAsync(
        () => Context.Set<TaskRow>().Where(task => task.Title == from).ExecuteUpdateAsync(task => task.SetProperty(row => row.Title, to), cancellationToken),
        $"rename in {Table}",
        cancellationToken);
```

- Violation: `ExecuteUpdate`, `ExecuteDelete`, or raw SQL called directly.
- Risk: the rules of [vp-postgres](library/architecture/spec/vp-postgres.skill/vp-postgres.skill.md#go-past-the-contract-with-a-method-of-its-own) break, and the compiler does not stop it.
- Fix: register the derived repository `Scoped` in `// [services]` under its own interface; [Statements.feature](./examples/src/Infrastructure/Postgres/Postgres.Tests/features/Statements.feature) shows both calls.

### Generate every migration
Change the row, run `make migration NAME={What}`, read what it wrote, and commit it with the row; apply with `make migrate` locally and with `App.Migrate` in a deployment, publishing it beside `App.Host` so the image has `/app/migrate`.
- Violation: a `HasPendingModelChanges` scenario removed; a migration edited after it was applied somewhere; `EnsureCreated` in the application.
- Risk: the model and the schema drift, and `MigrateAsync` stops the deployment; `EnsureCreated` leaves no history.
- Fix: a new migration for every further change. Decision recorded in [migration-job-as-a-project](./adr/migration-job-as-a-project.md).

### Register the readiness check
`AddPostgres` registers the check of `AspNetCore.HealthChecks.NpgSql` under the name `database` in the framework's registry, the same in every application, whether or not it has a health entry point.

```csharp
services.AddHealthChecks().AddNpgSql(config.Dsn, name: "database");
```

- Violation: a readiness check that sends a command; a `using` of `Api/Management` in the Postgres project; a line for the check in `Program.cs`.
- Risk: a check through a command fails on a business rule and holds traffic back for nothing; a type of the health entry point here stops the project building without it.
- Fix: the check opens a connection of its own, and [vp-health-in-dotnet](library/architecture/dotnet/vp-health-in-dotnet.skill/vp-health-in-dotnet.skill.md) reads the registry; with no health entry point nothing runs the check. `Postgres.Tests` takes the check from the registry by its name and runs it on a database that answers and on one that does not.

### Run the shared scenarios
Name the shared scenarios in [conformance.copy](./conformance.copy), run `make conformance-sync`, and implement their steps in `Postgres.Tests/Steps`, each comparing the fields of the row objects.
- Violation: a copy edited; a step comparing titles joined into one text.
- Risk: the contract is proved in another stack and not in this one.
- Fix: the sample tables and their specifications are in `Steps/SampleTables.cs`, created by `EnsureCreated` for the scenario; what only dotnet has stays in `ConfigForms.feature`, `ModelChanges.feature`, and `Statements.feature` beside the copies.

### Create the database of each scenario
Create a `TestDatabase` per scenario, apply `PostgresMigrations.ApplyAsync` where the scenario needs the schema, and dispose it after the scenario.
- Violation: `TestDatabase` in a static field; `DisableTestParallelization` removed from a project whose scenarios set the environment.
- Risk: scenarios see each other's rows.
- Fix: the database is created in a step and dropped in `[AfterScenario]`; the DSN of `TEST_DATABASE_DSN` needs `CREATEDB`.

# Check list
- [ ] The fixed files are unchanged copies of the templates; one `AppDbContext`, one migration history.
- [ ] Repositories and the services over them are scoped; `AddCommandScope()` follows every module; `ValidateScopes` is on.
- [ ] A specification uses only `Where`, `Include`, and `Select`; a projection's type has properties.
- [ ] A statement past the contract runs in `WriteAsync` or `ReadAsync`; no `IQueryable` leaves a repository.
- [ ] Every uniqueness rule has a unique index; names are snake_case.
- [ ] Every change of a row has its generated migration; the scenario on `HasPendingModelChanges` passes.
- [ ] `App.Migrate` is published as `/app/migrate`; `MIGRATE_ON_START` stays `false` beyond one instance.
- [ ] `make test` passes with `TEST_DATABASE_DSN` set; `bash test/check-vp-attach.sh` in this repository reports no file changed beyond [attach.allow](./attach.allow); `bash test/check-conformance.sh` reports no copy changed.
