# Problem
`Microsoft.AspNetCore.Grpc.JsonTranscoding` serves an annotated rpc over HTTP with no code; the Go catalog writes a route per rpc and generates the spec with grpc-gateway's `protoc-gen-openapiv2`. A spike on 2026-10-21 measured transcoding: errors as `google.rpc.Status`, proto-JSON, path parameters, and 501 for a deprecated rpc all match; a success is always 200 — `Response.StatusCode = 201` set in the method is overwritten; `Microsoft.AspNetCore.Grpc.Swagger` (0.10) lists only 200 and `default` and marks nothing deprecated, and builds the spec at run time.

# Selected variant
[[#Routes over the generated messages, spec by protoc-gen-openapiv2]]
- Owner decision, 2026-10-21: the HTTP form follows api-develop's success statuses and is the same as the Go service's for one proto contract.

# Searched variants

## Routes over the generated messages, spec by protoc-gen-openapiv2

**Selected.**

### Description
`ListsHandler.AddItemAsync(listId, request)` reads `AddItemRequest` with `ProtoJson.ReadAsync`, sends `AddItem`, answers `ProtoJson.Result(response, 201)`. `make proto-gen` runs `protoc` of `Grpc.Tools` with the release binary of `protoc-gen-openapiv2` v2.31.0; the googleapis and openapiv2 annotations are vendored under `third_party/proto/`.

### Benefits
- 201/202/200 by what the rpc did (api-develop's success-status-by-outcome); a Go and a dotnet service answer one contract the same way.
- The spec lists every status of every operation and marks a deprecated rpc; the example's spec is byte for byte the Go example's.

### Costs
- A route and its mapping per rpc, kept in step with the proto file by the contract scenario.
- One binary outside .NET, downloaded by `make proto-gen` for the platform; four vendored proto files.

## JSON transcoding

### Description
`AddGrpc().AddJsonTranscoding()`; the gRPC services mapped on the HTTP application too.

### Benefits
- No code per rpc; the official Microsoft path.

### Costs
- Every success is 200: a dotnet service answers a create 200 where the Go service of the same contract answers 201.
- The run-time spec describes neither the error statuses nor the deprecation.

## Transcoding with a middleware that sets the status from the proto

### Description
Transcoding, plus a middleware reading the rpc's `openapiv2_operation` and rewriting 200 to 201.

### Benefits
- Less code than routes per rpc.

### Costs
- Depends on the response not being sent yet when the middleware runs; the spec still needs protoc-gen-openapiv2.
