# Wave 1: shared client and service contracts

## Result and boundaries

The parent plan from PR #311 is the baseline. The shared `api-client` and
`app-layers` skills now define sibling domain/infrastructure/client/service
boundaries, API DTO returns, entity-focused partial clients, and a service that
adapts several clients of one external system. Same-system client sharing is an
exception requiring justification. The own-store entities-form exception remains.

Three owning ADRs record DTO conversion, grouping/cardinality, and sibling
boundaries. The historical return-value ADR is superseded; the naming and layer
ADRs are explicitly amended. Linked examples and all five sequence diagrams
follow the service-owned mapping contract.

Only two architecture specifications change in this wave: HTTP and gRPC client
links now point to the current shared DTO rule, and their Scope marks the old
rules/examples as pending wave 2. No executable example or template is migrated.

## Decisions and remaining questions

- Implement the owner's accepted responsibility and ownership rules first;
  keep actual stack migration in wave 2 as planned.
- Preserve full provider contract files while selecting only required operations.
- Map through public domain APIs; retain business invariants in domain behavior.
- Keep retry optional in the client pipeline, and preserve existing technical
  outcomes, deadlines, cancellation, request ids, logs and emulator guarantees.
- Generated gRPC messages versus client-owned API DTOs, exact .NET project layout,
  cross-module model ownership, and shared endpoint configuration are still open
  to the concrete stack design in wave 2.

## Accepted refinement: owned layer contracts

The owner accepted the split on 2026-11-28. `app-layers` now owns only the
responsibility/dependency map, sibling boundaries, interfaces and the call diagram.
`app-api-layer`, `app-command-layer` and `app-domain-layer` own implementation rules.
Integration-service realization stays in the providing mechanism (`api-client`
for API adaptation); no `app-service-layer` is introduced.

| Former app-layers requirement | Current owner |
|---|---|
| API parses and maps outcomes; independent dispatch | app-api-layer |
| Plain command input, names, result types | app-command-layer |
| Command factory, nested pipeline dispatch, consistency, identity | app-command-layer |
| One business invariant owner; public domain construction | app-domain-layer |
| Service adaptation of one external system and its clients | api-client |
| Layer testing boundaries | API/command/domain contracts and api-client; concrete engines remain covered by their existing VP tests |
| Allowed calls, own-store exception, interfaces, sibling folders, pure helpers | app-layers |

The independent-command ADR and its four diagrams moved to app-api-layer; the
command naming and nested-dispatch ADRs moved to app-command-layer. Their original
choices and dates are preserved. A new topology-owned ADR records the split.
The common handler contract previously defined by the base plateau now belongs
to app-command-layer; the plateau links it rather than defining another copy.

HTTP/gRPC/CLI API specs apply the common API contract. The base plateau and all
three stack layer extensions explicitly consume their implementation contracts,
so shortening app-layers does not silently remove requirements from consumers.
The develop README supplies navigation without reverse links from the layer map.

A separate audit of the final split found and corrected a downstream .NET storage
ADR link hidden in the topology's historical ADR: it would otherwise load the
implementation catalog back into app-layers. The reference is retained by name,
and the gate now rejects outgoing implementation links anywhere in the topology
skill's markdown/ADRs. The audit also corrected a migrated reference still labeled
app-layers and verified ownership of every former rule against the table above.

Validation: the expanded gate passes for five common contracts and 78 inventoried

## Protocol mechanics versus logical API adaptation

Owner clarification, 2026-11-28: client encapsulates endpoint calls, protocol-error
normalization and configured technical policies; service encapsulates API DTO to
Domain Model conversion and the API operations/clients realizing its consumer
method. Equivalent HTTP-to-gRPC replacement preserves service; logical API changes
are absorbed by client declarations and service realization while the consumer
contract remains implementable.

The protocol-neutral-client-contract ADR resolves the earlier representation
question: client-owned logical API DTOs and common technical outcomes cross into
service; transport-specific generated types and raw protocol exceptions do not.
Shared generated DTOs qualify when both protocols expose the same contract; an
extra handwritten type is not required solely because the DTO was generated. This is
mechanical wire conversion, not a move of domain mapping back into client.

Examples now distinguish multiple calls of one client from UserService owning
UsersClient and NamesClient of the same Identity system, each with its own API.
A separate protocol-swap diagram makes that change boundary visible. Permitting
service-to-service calls after a split into independent systems remains a proposed
architecture change; no new call edge is authorized by these examples.

A separate review checked equivalent transport replacement, remote error meaning,
service/domain mapping ownership, and one-client versus two-client examples. It
retained explicit unavailable-to-application-unavailable mapping and kept the
proposed cross-system service-call edge out of the accepted layer map. The shared
check gate and repository structural suite pass; no runtime files are changed.

## ADR lifecycle standard and applied archive

The owner requested that the reusable adr-create skill formalize archive handling.
It now distinguishes accepted and superseded records, moves fully replaced ADRs
and their exclusive assets under adr/superseded, removes active registration and
working references, and preserves history only behind the replacing ADR. Partial
amendments remain active for unaffected decisions. New/updated records carry
status; older unmarked records need no bulk migration. Moving alone does not
promise loader context exclusion.

The old client-side mapping record is archived accordingly. Its original decision
metadata and alternatives are preserved, with superseded status and a relative
replacement path; working skill/catalog/backlog references use the current DTO
ADR. The expanded check gate validates the authoring standard and checks that the
archive resolves to a replacement, is not actively registered, and is referenced
only by that replacement among the reviewed contracts.
