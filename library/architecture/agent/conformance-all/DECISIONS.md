# Shared scenarios for every variation point — decisions

One line per choice; ⚠️ marks a fork with real trade-offs, decided by the owner.

- ⚠️ 2026-11-04, owner: every spec skill gets `conformance/`: base-plateau, base-plateau-extension, vp-cli-api, vp-grpc-api, vp-http-api, vp-health, vp-http-client, vp-grpc-client, vp-client-retry; the missing scenarios of vp-postgres and vp-unit-of-work join theirs.
- ⚠️ 2026-11-04, owner: the stacks' texts merge by union, the stricter check wins; a stack that fails a merged scenario gets its code fixed.
- ⚠️ 2026-11-04, owner: vp-cli-api is not applied to dotnet; its scenarios run in Go and Python only.
- ⚠️ 2026-11-04, owner: one pull request into `arch-new-vp`, branch `arch-conformance-all`.
- 2026-11-04, agent: this supersedes error-shape's "no shared `conformance/` folder is added for the base plateau's log".
- 2026-11-04, agent: one folder per unit under `conformance/`, copied by one line of `conformance.copy` each; no `include` in the manifest, because a VP deletes some base units (`startup`) and an include could not leave them out.
- 2026-11-04, agent: a stack's own scenario file is named `{name}-in-{stack}.feature`; the existing ones (`kind_in_go.feature`, `go-payload.feature`, …) are renamed to it.
- 2026-11-05, agent: a scenario value is the output every stack writes (log level `INFO`, kind `not found`, bool `true`); dotnet's steps map their enum names to it.
- 2026-11-05, agent: the base log's "a failure of the service is written with its stack" is the stack's own in Python and dotnet (`json-log-in-{stack}.feature`): a Go error has no stack to write.
- 2026-11-05, agent: Go's "a middleware that passes on a value of another type" and dotnet's "a type that is no open generic behavior" / "no interceptor" are the stack's own: each tests a mechanism only that stack has.
- 2026-11-05, agent: the command logging scenarios log a command with a title (`{"title":"buy milk"}`), as dotnet did; Go and Python test with the same command shape. dotnet's recording logger writes through `JsonLogLine`, so every stack compares the JSON line.
- 2026-11-05, agent: the gRPC call log writes a code by its canonical name (`INVALID_ARGUMENT`) in every stack, as Python did; Go and dotnet wrote their own spelling (`InvalidArgument`), so one log pipeline read two names for one code.
- 2026-11-05, agent: Go's gRPC answers a failure of no kind INTERNAL and logs it as `grpc call failed` with its error, as Python and dotnet did; before, `Call` turned the error into a status itself and the cause never reached the log.
- 2026-11-05, agent: every stack rejects port 0 (`GRPC_LISTEN_PORT=0`), as dotnet did.
- 2026-11-05, agent: `rpcstatus` is owned by vp-grpc-api; vp-http-api's examples name it in their manifest.
- 2026-11-05, agent: vp-grpc-api's endpoint scenarios are two units, `grpc-contract` and `grpc-items`: the proto mode of vp-http-api extends ItemsService and keeps an `items.feature` of its own, and shares the contract.
- 2026-11-05, agent: the generic steps of the gRPC scenarios name gRPC (`the gRPC call should …`), as dotnet's did, so the HTTP steps of the same dotnet test project never collide with them.
- 2026-11-05, agent: vp-http-api's units are split by mode: `http-pipeline`, `http-contract`, `http-items` for the plain mode; `proto-*` units for what the proto mode adds or extends (its contract, items, lists, proto-JSON, the gRPC items, the lists' command, service and memory store). A unit two modes share is copied into both examples.
- 2026-11-05, agent: the docs scenario says what Swagger UI must do (load the spec from the prefixed URL, `/swagger` redirects under the prefix), not which asset files serve it: each stack's Swagger UI lays its files out its own way (Go `/swagger/`, Python `swagger-initializer.js`, dotnet `index.js`).
- 2026-11-05, agent: every stack rejects an HTTP body not declared as `application/json` (`Content-Type must be application/json`), as dotnet did; Go and Python's proto-JSON form now check it too.
- 2026-11-05, agent: Go's HTTP answers a failure of no kind INTERNAL and logs it as `http request failed` (`answerfailures.WriteFailure`, the logger put into the request's context by the middleware), as Python and dotnet did.
- 2026-11-05, agent: a route that needs a field answers 400 naming it (`body.text`): Python's framework does it; Go's and dotnet's test routes check the field themselves, as a route of the contract does.
- 2026-11-05, agent: Python's proto-JSON scenarios had no test module (`proto.feature` never ran); `proto_json_steps_test.py` runs them now.
- 2026-11-05, agent: Go's panic scenario stays Go's own (`answer-failures-in-go.feature`: the "http request panicked" record); the shared crash scenario checks the answer, the failed record, and that the server keeps serving.
- 2026-11-05, agent: vp-postgres changes the item lists service's scenarios; its file is named `item-lists-service.feature` like the shared one, and joins vp-postgres's conformance in wave 4.
- 2026-11-05, agent: the CLI's parse errors are checked by the argument they name (`bogus`, `--nope`), not by the framework's sentence (cobra's "unknown command", click's "No such command"): the words are the framework's, the argument named is the contract.
- 2026-11-05, agent: a crash of a CLI action is logged as `cli action crashed` in every stack; Go wrote `cli action panicked`.
- 2026-11-05, agent: a failed CLI run's answered record holds the arguments as given (`args`) in every stack, as Python did; Go held the flags parsed, which an unparsable run does not have.
- 2026-11-05, agent: Python's CLI prints the message of the error with a kind inside a wrapper (`Error: the name is taken`), as Go did; it printed the wrapper's text.
- 2026-11-05, agent: readiness has three outcomes in every stack, as dotnet had: a check that fails or panics/throws holds readiness back; a degraded one (Go `management.ErrDegraded`, Python `Degraded`) still takes traffic. Go recovers a check's panic.
- 2026-11-05, agent: dotnet's "the entry point of the composition root" scenarios stay dotnet's own (`serve-in-dotnet.feature`): they test the framework registry through which a VP registers its check; Go and Python add a check by a line in the composition root, with nothing to test beyond the server's own scenarios.
- 2026-11-05, agent: the client pipeline, the remote planner, and PlanRemoteItems are owned by vp-http-client; vp-grpc-client names them in its manifest (one file in both client examples of every stack).
- 2026-11-05, agent: the remote planner's scenarios name the API's answer by its canonical code (`answers INVALID_ARGUMENT with the message …`), as Go did: the service reads the code whatever transport answered it; Python and dotnet named an HTTP status and a number.
- 2026-11-05, agent: retry's "the caller's limit ends the wait" stays each stack's own (`retry-in-{stack}.feature`): a Go context carries a deadline checked before a wait; Python's cancellation passes through as it is; dotnet's ends the call with the last attempt's outcome.
- 2026-11-05, agent: the gRPC client's "the generated code describes the copied contract" is Go's and Python's own (`contract-in-{stack}.feature`): dotnet compiles the contract at every build and has nothing to drift.
- 2026-11-05, agent: base-plateau-extension's scenarios were already the same text in every stack; they move into spec as `command-access`, `batch-limit`, `http-authentication`.
- 2026-11-05, agent: the shared scenarios of vp-logging, vp-postgres, vp-unit-of-work move into one folder per unit (`masked/`, `postgres/`, `unit-of-work/`), as every other spec skill's: vp-postgres needs a second unit (`postgres-item-lists-service/`) copied elsewhere.
- 2026-11-05, agent: vp-postgres's `statements` was the same in every stack and joins its shared scenarios; its item lists service's scenarios become `postgres-item-lists-service`. `config-forms` and `model-changes` stay each stack's own: the DSN forms are the driver's (Npgsql key=value, Go and Python a URL), the model check is the migration tool's (EF, goose, Alembic).
- 2026-11-05, agent: dotnet's `command-scope-in-dotnet.feature` (MediatR's scopes), the vp-logging payload files (`payload-in-{stack}.feature`), Python's `repository-in-python.feature` and `unit-of-work-in-python.feature` are renamed as each stack's own.
- ⚠️ 2026-11-05, open: dotnet's `Persistence.feature` and `Migrate.feature` (the application over PostgreSQL: a restart, migrate on start, the migrate job) have no counterpart scenarios in Go and Python, which have the code (`cmd/migrate`, `MIGRATE_ON_START`) but no process-level tests; sharing them means writing those suites.
- ⚠️ 2026-11-05, open: vp-unit-of-work's middleware differs by design between stacks: a failed commit is `unavailable` with its cause in Go and Python, its own error in dotnet; Go and Python's unit of work is asked to `begin`, dotnet's opens on the first write; Go checks the pool and that no transaction stays open in the nested commands, dotnet does not; dotnet tests ImportItems on its own. Sharing them changes dotnet's middleware and Go/Python's tests.
