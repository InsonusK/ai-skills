# dotnet entities — decisions

One line per choice; ⚠️ marks a fork with real trade-offs, decided by the owner.

- ⚠️ 2026-11-05, owner: dotnet maps the domain's entities with EF Core; the database is the service's own store, not an external system, so no row layer stands between them. Go and Python keep rows.
- ⚠️ 2026-11-05, owner: one mechanism for simple and composite tables; a technical table (outbox, inbox, a cache of another system's data) maps a class of the infrastructure in the same context.
- ⚠️ 2026-11-05, owner: specifications live beside the entity, in `{Module}.Domain`.
- ⚠️ 2026-11-05, owner: the database's failures become kinds in one command middleware.
- ⚠️ 2026-11-05, owner: the locks of an aggregate are the consumer's choice; a pessimistic lock is a variation point of its own (`vp-row-lock`, later).
- ⚠️ 2026-11-06, owner: Ardalis's repository and specifications as they are, in place of our repository and selector, in dotnet.
- ⚠️ 2026-11-06, owner: a handler takes `IRepository<T>`; the in-memory base of `vp-http-api-in-dotnet` moves to the same interface, so attaching the database changes no handler.
- ⚠️ 2026-11-06, agent, for review: no `EntityFramework.Exceptions`. Its processor covers `SaveChanges` only, not a query, `ExecuteUpdate`, or raw SQL, so the translation by SQLSTATE over the chain of causes (`StoreFailures`) is still needed and already covers every path; the package would add a dependency and a second way to read the same failure.
- 2026-11-06, agent: `IAggregateRoot`, `IRepository<T>`, `IReadRepository<T>` in `Shared/Persistence`, as in Ardalis's Clean Architecture template; a child gets no repository.
- 2026-11-06, agent: a failed save clears the change tracker, so the shared scenario "A failed write leaves nothing pending" holds; a successful one keeps the tracked entities for the rest of the command.
- 2026-11-06, agent: `CountAsync`, `AnyAsync`, `DeleteRangeAsync` of `PostgresRepository` refuse a specification with a page (the risk of ADR `order-and-page-on-the-selector`).
- 2026-11-06, agent: the example's aggregate is the list: `ItemList` (the caller's id, `IAggregateRoot`) owns its `Item`s and guards the rule "a title is unique in its list" in `Add`, with the rule's message; the unique index answers a race through the middleware. So wave 2 (an aggregate with children) joins wave 1; `PlanItems` keeps `Item`s that belong to no list.
- 2026-11-06, agent: `MemoryRepository<T>` keeps the root objects in one `MemoryStore` singleton (one store behind `IRepository<>` and `IReadRepository<>`); a count, an existence check, and a delete apply the conditions only (`IsSatisfiedBy`) and refuse a page, as the database's repository does (`Shared.Persistence.SpecificationPage`).
- 2026-11-06, agent: the handlers' scenarios run over `MemoryRepository<T>` (a subclass adds a failure and "asked"), not a hand fake of Ardalis's 22 methods; the Memory project stays in the database's example for them.
- 2026-11-06, agent, after the audit of wave 1: `MemoryRepository` refuses a root whose `Id` it keeps already (`Conflict`), as the primary key does; concurrent changes of one shared root stay unguarded in memory, said in its comment. `WriteAsync` saves through the class's own `SaveChangesAsync` and returns to its savepoint after any failure of the statement, a deadlock included, dropping only a rollback that finds no connection. `StoreFailuresMiddleware` gets scenarios of its own in `Middleware.Tests`. The spec marks its remaining selector-only rules as the rows form's; the shared scenario "Update of the selector is all or nothing" stays in `conformance/` (an update of several rows, all or nothing, is behaviour of both forms; dotnet runs it as a list and `UpdateRangeAsync`).
- ⚠️ 2026-11-06, owner: #292 (row version over rows) is set aside; the new approach is collected in `arch-db-entities`, stage by stage.
- 2026-11-06, agent, on the base after #293: dotnet stops copying the scenarios only the rows form has: `vp-postgres`'s `postgres-selector/` (moved out of `postgres/`) and `postgres-item-lists-service/`, and `vp-http-api`'s `proto-item-lists-service/` and `proto-memory-lists/`; the shared handler scenarios `proto-item-lists/` stay, their "item lists" being the repository; dotnet-only scenarios are named `{name}-in-dotnet.feature`.
- ⚠️ 2026-11-06, owner, on the review of #294: the base plateau has no memory and no entry point; the API variation point adds a way to call the application but no memory. So the HTTP proto example keeps its lists in the process (`KeptLists`, a plain class the module registers) with no repository and no Ardalis; `MemoryRepository` leaves it. A variation point of its own for a store in memory (`vp-inmemory-in-dotnet`) only if a need appears. Replaces "the in-memory base moves to the same interface": attaching the database changes the example's sample handlers, as `vp-postgres` describes how a handler takes `IRepository<T>` from DI.
- 2026-11-06, agent: the repository in memory stays as a test helper of the database's variation point: `Postgres.Testing/InMemoryRepository<T>`, for the handlers' scenarios, its own scenarios in `Postgres.Tests`. dotnet copies no `proto-item-lists/` either: its proto handlers keep no store a scenario could fail; its handler scenarios are `item-lists-in-dotnet.feature`.
- ⚠️ 2026-11-06, owner: the repository's contract lives in its own project `src/Shared.Persistence` (namespace `Shared.Persistence`), so `Shared` keeps no package; the core `app-layers` names the repository of the own store as what a command calls in the entities form, in place of a service (ADR `service-wraps-one-infrastructure` amended).
- ⚠️ 2026-11-07, owner, after the form of `plateau-offline-sync-service`: an entity is a row of its table; `ItemList` and its `lists` table go, `Item` gets its key and its list, the unique index holds one title per list and the handler checks it first. The configuration of a module's tables lives in `{Module}.Domain/Configurations` (EF Core's relational model API in the domain, no provider), `AppDbContext` applying each module's configurations. Specifications live in `{Module}.Application/Specifications`. No `IAggregateRoot`: `IRepository<T>` takes `T : class`. Replaces the aggregate of 2026-11-06.
- ⚠️ 2026-11-07, owner: the unit of work stays as it is (each write saves, the transaction opened on the first one, committed at the end); the comparison with one SaveChanges at the end is kept in ADR `a-store-saves-at-once` of `vp-postgres-in-dotnet`.
- ⚠️ 2026-11-07, owner: the rule "a variation point does not edit its base's files" is under question (`library/architecture/README.md`, Layout); a natural change of a base file is made, listed, and said.
