# Problem
Go chains `grpc.UnaryServerInterceptor`s, which see the request, the response, and the error of a call; dotnet uses `Grpc.AspNetCore` interceptors of the same reach. Python needs an asyncio-native server ([async-handlers](library/architecture/python/base-plateau-in-python.skill/adr/async-handlers.md)) whose middleware can do the same: a call log needs the request, the response, and the status; the answer of failures needs the exception.

# Selected variant
[[#grpc.aio with a chain of plain middleware]]
- Owner decision, 2026-10-25: grpcio's `grpc.aio`.

# Searched variants

## grpc.aio with a chain of plain middleware

**Selected.**

### Description
grpcio's `grpc.aio.server`, the services generated by `grpcio-tools` and typed by `mypy-protobuf`. The server is given one `grpc.aio.ServerInterceptor` (`_Chain`): it takes the method handler the generated code registered and, for a unary call, returns one whose behaviour builds an `IncomingCall` (method, request, context) and runs it through the chain - `CallLogMiddleware`, `AnswerFailuresMiddleware`, the list of `entry` - to the method. A middleware is `async (call, call_next) -> response`, the shape of the HTTP API's middleware.

```
grpc.aio server ─▶ _Chain ─▶ CallLogMiddleware ─▶ AnswerFailuresMiddleware ─▶ [the list] ─▶ method
                  (one ServerInterceptor)        aborts with the status of the error's kind
```

### Benefits
- The reference implementation of gRPC with its C core: HTTP/2, reflection (`grpcio-reflection`), and graceful stop (`server.stop(grace)`) as every other language has them.
- A middleware sees what Go's interceptor sees - the request, the response, the exception - and runs inside the call's task, so the request id it sets (`ContextVar`) is the command's.
- One shape of middleware for HTTP and gRPC; writing one needs no knowledge of grpc's handler objects.

### Costs
- The chain is code of the template (`_Chain`, `_step`), not of the library.
- A streaming method passes the chain unchanged: the variation point covers unary methods only.
- grpcio's own type stubs come from separate packages (`types-grpcio`, `types-grpcio-reflection`), and the generated servicer is abstract only in the stub `mypy-protobuf` writes, so a method missing from a servicer fails `make lint`, not the build.

## grpc.aio with its own ServerInterceptor per middleware

### Description
Each middleware a `grpc.aio.ServerInterceptor`, given to `grpc.aio.server(interceptors=[...])` in order.

### Benefits
- The library's documented extension point; no chain of the template's own.

### Costs
- `intercept_service` runs before the call with only the method's name and metadata; to see the request, the response, or the exception, each middleware must unwrap the method handler and build a new one with its deserializer and serializer - the same wrapping as the selected variant, repeated in every middleware.

## grpclib (with betterproto)

### Description
The pure-Python asyncio gRPC library with its own code generator, events for middleware (`RecvRequest`, `SendTrailingMetadata`).

### Benefits
- Pure Python, no C extension; dataclass messages from betterproto.

### Costs
- A smaller user base than grpcio, and the messages come from a second generator, not from the `protoc` plugins every other stack of the catalog uses.
