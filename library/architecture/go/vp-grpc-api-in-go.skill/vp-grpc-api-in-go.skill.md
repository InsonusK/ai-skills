# Goal
- **The gRPC variation point in Go** - A Go application that keeps every property of [vp-grpc-api](library/architecture/spec/vp-grpc-api.skill/vp-grpc-api.skill.md); this skill details that skill's implementation for Go and restates none of its rules.
- **Attached by the listed changes only** - Attaching it adds files and changes only the base files [attach.allow](./attach.allow) names, which the repository's attach check verifies against [base-plateau-in-go](library/architecture/go/base-plateau-in-go.skill/base-plateau-in-go.skill.md)'s example.

# Core Principle
- **Copied once, written per command** - The entry point is split as [app-layers-in-go](library/develop/go/app-layers-in-go.skill.md#split-each-entry-point-into-pipeline-endpoint-and-registration) requires: `pipeline/` is copied from templates and never edited; per command the application writes, in its service's file of `endpoint/`, a handler field, a method, and its two mappings.

```
docs/integration/api/todo/todo.proto   the contract, written by hand
gen/api/todo/*.pb.go                   generated by make proto-gen, committed
internal/api/core/rpcstatus/                copied from error-kinds-in-go; the same in every network entry point
internal/api/grpc/
├── pipeline/                          copied from templates, never edited (grpcpipeline)
│   ├── config.go  call.go  server.go
│   ├── logging.go  recover.go         one file per interceptor: the call log, panic recovery
│   └── features/  test/               the fixed code's scenarios, with a test service of their own
├── endpoint/                          written per application, grows with the API
│   ├── items.go                       ItemsHandler: one file per proto service ≈ an ASP.NET controller
│   └── features/  test/               one feature per service + the contract scenario
└── services.go                        Endpoints (one field per service), Services, Run (grpcapi)
```

# Rule

## MUST

### Copy the entry point from templates
Fill and copy [config.go](./templates/internal/api/grpc/pipeline/config.go), [call.go](./templates/internal/api/grpc/pipeline/call.go), [server.go](./templates/internal/api/grpc/pipeline/server.go), [logging.go](./templates/internal/api/grpc/pipeline/logging.go), and [recover.go](./templates/internal/api/grpc/pipeline/recover.go) to `internal/api/grpc/pipeline/`, and `rpcstatus.go` of [error-kinds-in-go](library/develop/go/error-kinds-in-go.skill/error-kinds-in-go.skill.md) with its scenarios (the example's `internal/api/core/rpcstatus/`) unless another entry point already put them there, replacing `{module-path}` with the module path from `go.mod`.
- Risk: a retyped server drifts in its error mapping, panic recovery, or shutdown from every other Go service of the catalog.
- Fix: copy the files; after filling, searching them for `{module-path}` returns nothing.

### Write the contract and generate its code
Write `docs/integration/api/{contract-name}/{file}.proto` as [todo.proto](./examples/docs/integration/api/todo/todo.proto) shows — `// version:` first, `package {name}.v{major};`, `option go_package = "{module-path}/gen/api/{contract-name}";` — and generate `gen/api/{contract-name}/` with `make proto-gen` from [buf.yaml](./templates/buf.yaml) and [buf.gen.yaml](./templates/buf.gen.yaml) at the repository root, per [api-develop-in-go](library/common-workflow/develop/api-develop-in-go.skill/api-develop-in-go.skill.md)'s layout. Without the HTTP form, the proto file has no `google.api.http` annotations, and buf needs neither the googleapis dependency nor `protoc-gen-openapiv2`.
- Violation: message types written by hand; generated files edited or not committed; a generator installed with `go install …@latest`.
- Risk: the server and its clients disagree on the wire format; an unpinned generator writes different code on another machine.
- Fix: the generators are `tool` lines of `go.mod` (see [Add the gRPC modules](#add-the-grpc-modules)); run `make proto-gen` after every proto change and commit the result.

### One file per service in the endpoint package
Write each service of the proto contract in its own file `internal/api/grpc/endpoint/{service}.go`, the counterpart of an ASP.NET controller: an exported `{Service}Handler` struct (`ItemsHandler`) with one `pipeline.Handler[TCommand, TResult]` field per method, its method `Service() grpcpipeline.Service` returning `{Desc, Impl}`, a server struct embedding the generated `Unsafe{Service}Server` with `var _ {pkg}.{Service}Server = …{}` beside it, one method per rpc returning `grpcpipeline.Call(ctx, handler, req, decode, encode)`, and a `decode` and an `encode` per method. Keep in `internal/api/grpc/services.go` only `Endpoints`, one field per service, `Services(e Endpoints)`, and `Run(ctx, e, logger)`.
- Violation: a service's methods written in `pipeline/`; the server struct embedding `Unimplemented{Service}Server`; a generated message passed to a command.
- Risk: application code mixed into the copied package is lost when the templates are copied again; with `Unimplemented…` embedded, an rpc added to the proto file and forgotten here compiles and answers `UNIMPLEMENTED` in production.
- Fix: follow the example's [items.go](./examples/internal/api/grpc/endpoint/items.go) and [services.go](./examples/internal/api/grpc/services.go); the assertion fails the build when a method is missing.

### Replace the startup entry in main.go
Replace the startup `entry.Entry` in the `// [entries]` list of `cmd/{app}/main.go` with a `grpc` one calling `grpcapi.Run` with `grpcapi.Endpoints`, filled with the handlers built in `// [handlers]`, and delete `internal/api/startup/`.

```go
// [entries] - every entry point, one Entry each, run together by entry.RunAll.
endpoints := grpcapi.Endpoints{Items: endpoint.ItemsHandler{PlanItems: planItems}}
err = entry.RunAll(ctx, logger,
	entry.Entry{Name: "grpc", Run: func(ctx context.Context) error {
		return grpcapi.Run(ctx, endpoints, logger)
	}},
)
return entry.ExitCode(err)
```

- Violation: the settings loaded or the server built in `main.go`, `grpcapi.Run` called outside `entry.RunAll`, or the startup entry kept beside it.
- Risk: every line of the entry point's start in `main.go` is a line each later variation point's instruction must step around; a server started outside the list is not stopped when another entry point fails.
- Fix: import `grpcapi "{module-path}/internal/api/grpc"` and `"{module-path}/internal/api/grpc/endpoint"`; other entries of the list (health, HTTP) stay as they are.

### Add the gRPC modules
Add `google.golang.org/grpc` at `v1.84.0` and `google.golang.org/protobuf` at `v1.36.12`, and the generators as tools: `go get -tool github.com/bufbuild/buf/cmd/buf@v1.73.0 google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.12 google.golang.org/grpc/cmd/protoc-gen-go-grpc@v1.6.2`; then `go mod tidy`.
- Risk: an unpinned version builds a different server or generates different code on another machine.
- Fix: commit `go.mod` and `go.sum` with these versions.

### Cover the entry point with scenarios
Copy the example's `internal/api/grpc/pipeline/features/` and `test/` unchanged but for the module path in their imports: they cover the fixed code through an in-memory server (`bufconn`) and a test service of their own — the error mapping, a panic, reflection on and off, the settings, and `Run` with a call in flight during the stop. In `internal/api/grpc/endpoint/` write one feature per service, calling it through the generated client with its handlers faked (`pipeline.HandlerFunc`), and the contract scenario comparing `grpcapi.Services` with the services of the generated file descriptor; tag them `@type/api/grpc` and `@type/tech-check`.
- Risk: a variation point without scenarios lets a change in the error mapping or the shutdown reach production unnoticed; a service feature that repeats the error mapping grows the suite with every service and tests nothing new.
- Fix: a service feature checks only its own decoding and encoding; `make test` passes.

## SHOULD

### Serve a new command in its service's file
Serve a further command of an existing service by adding its rpc and messages to the proto file, running `make proto-gen`, and adding its field, its method, and its `decode` and `encode` to the service's file in `endpoint/`, its scenario to the service's feature, and its handler to the service's `{Service}Handler` in `main.go`; a new service adds its file and feature, one field of `Endpoints`, one line of `Services`, and one row of the contract scenario.

### Answer a deprecated rpc with grpcpipeline.Unimplemented
Return `grpcpipeline.Unimplemented("{Rpc} is deprecated since {version}")` from the method of an rpc marked `option deprecated = true`, calling no command; its HTTP form answers 501 with the same message.

# Check list
- [ ] `internal/api/grpc/pipeline/{config,call,server,logging,recover}.go` and `internal/api/core/rpcstatus/rpcstatus.go` are filled copies of the templates; no placeholder is left.
- [ ] `docs/integration/api/{contract-name}/{file}.proto` is versioned per api-develop; `make proto-gen` leaves no diff; the generators are `tool` lines of `go.mod`.
- [ ] Each proto service has its own file in `endpoint/` with its `{Service}Handler` and `Service()`, a server embedding `Unsafe{Service}Server` with the interface assertion, and per method its `decode` and `encode`; `services.go` holds only `Endpoints`, `Services`, and `Run`.
- [ ] The `// [entries]` list of `main.go` has a `grpc` entry calling `grpcapi.Run` with `grpcapi.Endpoints`; `internal/api/startup/` is deleted.
- [ ] `make test` passes with the fixed code's features, one feature per service, and the contract scenario.
- [ ] `bash test/check-vp-attach.sh` in this repository reports no base file changed beyond [attach.allow](./attach.allow).
