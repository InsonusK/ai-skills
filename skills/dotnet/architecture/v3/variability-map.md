**VP2's Constraint, checked against the actual catalog:** `solution-command-integration` is currently unconditional core (every existing plateau past `plateau-stateless-non-interactive-service` includes it in `created_by` — no plateau in this catalog skips it). The constraint is therefore always trivially satisfied *today*; it is still recorded, and now backed by a real `depends_on` (see [[skills/dotnet/architecture/v3/plateau/plateau-service-with-api/adr/require-at-least-one-mediatr-source.md|the ADR that added it]]), because it becomes load-bearing the moment a future plateau ever introduces a module without `solution-command-integration` (e.g. a read-only/query-proxy variant) — at that point this constraint is what would correctly block `HttpApi=Yes` on such a module until a MediatR source exists.

**VP4's constraint, why it is not in the Constraint column:** [[skills/dotnet/architecture/v3/solutions/solution-domain-rules.skill/solution-domain-rules.skill.md|solution-domain-rules]]'s own Boundaries state it "does not decide *which* duplicated condition is worth centralizing, or *when* — that judgment call is made by whoever is applying it, based on real, observed duplication or drift, not on speculation." This is a process precondition (has duplication actually been observed?), not a structural one the catalog can check mechanically — unlike VP0/VP2's constraints, nothing in `depends_on`/`built_on_plateau` could encode it, so it stays documented in prose rather than forced into the Constraint column.

# Core (not Variation Points)
Everything in [[skills/dotnet/architecture/v3/plateau/plateau-stateless-non-interactive-service/plateau-stateless-non-interactive-service.skill/plateau-stateless-non-interactive-service.skill.md|plateau-stateless-non-interactive-service]]'s `created_by` (`solution-sln-structure`, `solution-pipeline-registration`, `solution-mediator-exception-handler`, `solution-dotnet-conformance-testing`) and [[skills/dotnet/architecture/v3/plateau/plateau-service-with-validated-module-interaction/plateau-service-with-validated-module-interaction.skill/plateau-service-with-validated-module-interaction.skill.md|plateau-service-with-validated-module-interaction]]'s own `created_by` (`solution-value-objects`, `solution-validation-behavior`, `solution-domain-behaviour`, `solution-dto-property-validators`, `solution-command-integration`) is **not** a Variation Point: no plateau in this catalog skips any of it, so per [[skills/common-workflow/architecture/design/plateau-map/variability-map-create.skill/variability-map-create.skill|variability-map-create]]'s own test, two teams building on this catalog today cannot legitimately disagree about including it. **A legal combination with no named plateau yet:** VP0=Yes and (VP2=Yes or VP3=Yes) with VP4=No — a persisted module with an external API but no centralized rules — violates no stated Constraint but has no dedicated plateau today. `plateau-v1` always brings VP4=Yes along via `plateau-shared-rules`.
