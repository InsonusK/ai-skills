## Variation Points

Each row is one axis on which two modules built on this family could legitimately answer differently. Common baseline features from the Feature Model (`SoftValueObjects`, `ValidationPipeline`, `ExceptionHandlingPipeline`, `CrossModuleValidation`, `MediatorModuleIntegration`, `AppLogging`, `TestConformance` + its four children) are **not** rows here — every path through the family includes them, so per the parent skill's test they are shared core, not variability. See [Grouping features and selectors that are not VPs](#grouping-features-and-selectors-that-are-not-vps).

### VP2's constraint — Persistence requires DomainLogic

Confirmed by the family's owner and now drawn as `Persistence -. "Requires" .-> DomainLogic` in the [feature diagram](skills/dotnet/architecture/feature/diagrams/feature-diagram.mmd). Evidence:

- **Feature Model:** [[skills/dotnet/architecture/feature/feature-model\|feature-model.md]] states `{Module}.Domain` "only appears once `DomainLogic` is selected." Persisted entities live in `{Module}.Domain`; `solution-domain-configuration` extends `{Module}.Domain.Entities.Entity.cs`, and `solution-repository-integration` extends `{Module}.Domain.csproj`. Without VP1 there is no Domain project for Persistence to store from.
- **v3:** `plateau-statefull-service` has `parent_plateaus: plateau-service-with-validated-module-interaction`, which composes `solution-domain-behaviour` (= DomainLogic). Every persistence solution's `built_on_plateau` sits on top of that plateau — Persistence has never been applied to a module without DomainLogic in v3.

Still not backed by a `depends_on` edge (v3's persistence solutions declare no dependency on `solution-domain-behaviour`). Follow-up: when v3.1 authors its own persistence solutions, encode this dependency in `depends_on`, recorded as a plateau-level ADR.

### VP3's constraint (not yet encoded in any `depends_on`)

The Feature Model originally drew `ValueObjects --> DomainLogic` **and** `ValueObjects --> Persistence` jointly as an OR. Once `Persistence -> DomainLogic` was made explicit (see the VP2 note above), the `ValueObjects --> Persistence` edge became redundant — every model with `Persistence` already has `DomainLogic`, so `(VP1 OR VP2)` collapses to `VP1` — and has been **dropped from the diagram**. The constraint is now simply **`ValueObjects` requires `DomainLogic`**: the strict `{ValueObject}` lives in `{Module}.Domain`, which only VP1 introduces.

Not backed by a `depends_on` edge — `solution-value-objects` in v3 has an empty `depends_on`. Follow-up: when v3.1 authors its own strict-Value-Object solution, that solution's `depends_on` should encode the dependency on the DomainLogic solution, recorded as a plateau-level ADR.

### VP4's precondition (why it is not in the Constraint column)

[[skills/dotnet/architecture/solutions/solution-domain-shared-rules.skill/solution-domain-shared-rules.skill|solution-domain-shared-rules]]'s own Boundaries state it "does not decide *which* duplicated condition is worth centralizing, or *when* — that judgment call is made by whoever is applying it, based on real, observed duplication or drift, not on speculation." This is a process precondition (has duplication actually been observed?), not a structural one the catalog can check mechanically — nothing in `depends_on`/`built_on_plateau` could encode it — so it stays in prose, exactly as in the [v3 map](skills/dotnet/architecture/v3/variability-map.md).

### VP8's constraint (satisfied by construction in this family)

In [v3](skills/dotnet/architecture/v3/variability-map.md), `HttpApi=Yes` required `(CommandIntegration=Yes OR QueryIntegration=Yes)` — see [[skills/dotnet/architecture/v3/plateau/plateau-service-with-api/adr/require-at-least-one-mediatr-source.md|that ADR]]. In v3.1 the Feature Model makes `MediatorModuleIntegration` (Command + Query dispatch) a **common** feature, so `solution-http-api-publication`'s `depends_on` on `solution-query-integration` + `solution-command-integration` is always satisfied. The constraint is kept in mind but is inert unless a future variant ever removes MediatR dispatch from the common baseline (e.g. a pure pass-through proxy module).

## Grouping features and selectors that are not VPs

Following the Feature Model's own "deliberately not rows" note and [[skills/common-workflow/architecture/design/plateau-map/variability-map-create.skill/variability-map-create.skill.md|variability-map-create]]'s Or-group rule:

- **`SyncInboundApi` / `SyncOutboundApi`** — umbrella features, each an `At least one (protocol)` parent of two independently-optional transports. They get no VP row of their own: `SyncInboundApi` ≡ `(VP8=Yes OR VP9=Yes)` and `SyncOutboundApi` ≡ `(VP10=Yes OR VP11=Yes)`. A module's inbound-sync surface is therefore one of the four states {none, HTTP, gRPC, HTTP+gRPC}, read directly off the VP8 × VP9 pair — **this is exactly the "No / any combination of HTTP, gRPC" intent**, expressed as two Yes/No rows rather than a 4-item categorical variant list. Per [[skills/common-workflow/architecture/design/plateau-map/variability-map-create.skill/variability-map-create.skill.md|variability-map-create]]: an "Or" group (freely combinable, not mutually exclusive) is always separate boolean VPs, never enumerated combinations — so that adding a third transport later is one new row, not a doubling of the variant list. The `At least one (protocol)` edge only says you cannot have the umbrella *concept* with zero transports; since the umbrella is not itself selectable (only the transports are), there is no separate legality constraint to record.
- **`AsyncInboundApi` / `AsyncOutboundApi`** — kept **as** VPs (VP12, VP13) because each is 1:1 with a single `Mandatory` realization (`KafkaConsumer`, `KafkaProducer`), not an "at least one of N" group.
- **Entity classification** (Internal/External × Immutable/Mutable) — *not* an input selector but the **consequence** of the VP5 × VP6 combination per entity: Immutable/Mutable = VP5 (concurrency control) No/Yes, Internal/External = VP6 (external identity) No/Yes → one of 4 named states. It has no independent Yes/No, so it is not a VP. [[skills/dotnet/architecture/solutions/solution-entity-classification.skill/solution-entity-classification.skill\|solution-entity-classification]] is a **feature-combination resolver** — a solution that exists only to spell out explicitly what each VP5 × VP6 combination produces. Per the owner, a combination-resolver solution is a warning sign of coupling between two VPs that ought to be independent; it is tolerated here because it is the only one so far. VP7 (`AuditTimestamps`) is a third, genuinely independent per-entity axis (any user-initiated entity), not part of this 4-state classification.
- **Cecil architecture tests** — a mandatory companion of VP4, never applied independently. Not a VP; folded into VP4's **Realized by**.

## Out of scope

- **VP10–VP14 are skeletons.** Their solution skills exist in `v3.1/solutions/` with a `> Draft contract` marker and one shape-only Implementation file; full authoring is deferred until a real consumer exists. Their Constraints/notes come from the Feature Model, not working code.
- **VP10–VP14 are unrealized.** They come from the Feature Model's intended-Program-Family scope. Their Variants, Constraints, and "Mandatory realization" notes are taken from the Feature Model diagram, not from working solutions — treat them as provisional until authored.
- **Constraint evidence is uneven.** VP5–VP7's `requires VP2` is backed by real `depends_on` edges in the v3 entity solutions. VP2's `requires VP1` and VP3's `requires VP1` are drawn as `Requires` edges in the feature diagram (owner-confirmed) but not yet in any `depends_on` — the v3 solutions predate this decision. VP14's `requires VP13 AND VP2` is Feature-Model reasoning only (aspirational). The absence of other Constraints reflects this pass, not a proof.
- **Feature Model was updated during this step** (owner-confirmed): added `Persistence -. "Requires" .-> DomainLogic`; removed the now-redundant `ValueObjects -. "Requires" .-> Persistence`, keeping only `ValueObjects -. "Requires" .-> DomainLogic`. The [feature diagram](skills/dotnet/architecture/feature/diagrams/feature-diagram.mmd) and [feature-model.md](skills/dotnet/architecture/feature/feature-model.md) now match this map.
- **Migration is `No` everywhere** — no case in this family has yet been observed changing a VP answer after a module was already composed. Per the parent skill, `Migration` is set `Yes` only on a real observed transition, never speculatively.
- **The VP5 × VP6 combination-resolver (`solution-entity-classification`) is a known smell**, not a clean pattern — it couples two VPs the map otherwise treats as independent. Kept because it is the only instance; a second one should trigger a rethink of how per-entity axes are modelled.
- **The plateau↔VP view lives outside this map** — see [plateau/plateau-repository.md](skills/dotnet/architecture/plateau/plateau-repository.md); this file intentionally ends at the VP↔solution binding.
- **Entity-level VPs (VP5–VP7) are answered per persisted entity**, not once per module — the only rows in this map at that granularity, matching the Feature Model's mixed-granularity note.
