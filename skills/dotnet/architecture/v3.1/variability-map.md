# skills/dotnet/architecture/v3.1 Variability Map

Built per [[skills/common-workflow/architecture/design/plateau-map/variability-map-create.skill/variability-map-create.skill|variability-map-create]], from the non-common features of [[skills/dotnet/architecture/v3.1/feature/feature-model.md|v3.1/feature/feature-model.md]] (the Feature Model produced by the previous pipeline step). This map is the input to [[skills/common-workflow/architecture/design/plateau-create-by-solutions.skill/plateau-create-by-solutions.skill.md|plateau-create-by-solutions]].

**Status of this catalog.** `v3.1/` currently holds only `feature/` and `design/` — it has no `plateau/` or `solutions/` folders of its own yet. `v3.1` is an explicit re-modelling of the existing [[skills/dotnet/architecture/v3/README.md|v3]] catalog (see the Feature Model's own header), so every **Realized by** cell below links into `v3/solutions/` as the family's *current* realization. Rows whose realization does not exist anywhere yet are marked **aspirational** — they come from the Feature Model's intended-Program-Family scope, not from working code. When `v3.1` grows its own `solutions/`, re-point these cells and drop the aspirational markers.

## Variation Points

Each row is one axis on which two modules built on this family could legitimately answer differently. Common baseline features from the Feature Model (`SoftValueObjects`, `ValidationPipeline`, `ExceptionHandlingPipeline`, `CrossModuleValidation`, `MediatorModuleIntegration`, `AppLogging`, `TestConformance` + its four children) are **not** rows here — every path through the family includes them, so per the parent skill's test they are shared core, not variability. See [Grouping features and selectors that are not VPs](#grouping-features-and-selectors-that-are-not-vps).

### VP3's constraint (flagged, not yet encoded in any `depends_on`)

The Feature Model records exactly one cross-tree constraint: the two `Requires` edges `ValueObjects --> DomainLogic` and `ValueObjects --> Persistence`, **jointly an OR** (either one alone satisfies it — [[skills/dotnet/architecture/v3.1/feature/feature-model.md\|feature-model.md]] states this explicitly, since mermaid edge labels cannot). The evidence is architectural, from the Feature Model: `{Module}.Domain` (where the strict `{ValueObject}` lives) does not exist at the common baseline and only appears once `DomainLogic` or `Persistence` is selected. It is **not** currently backed by a `depends_on` edge — `solution-value-objects` in v3 has an empty `depends_on`. Per [[skills/common-workflow/architecture/design/plateau-map/variability-map-create.skill/variability-map-create.skill.md|variability-map-create]]'s rule, this is flagged: when v3.1 authors its own strict-Value-Object solution, that solution's `depends_on` should encode the dependency, recorded as a plateau-level ADR.

### VP4's precondition (why it is not in the Constraint column)

[[skills/dotnet/architecture/v3/solutions/solution-domain-rules.skill/solution-domain-rules.skill.md|solution-domain-rules]]'s own Boundaries state it "does not decide *which* duplicated condition is worth centralizing, or *when* — that judgment call is made by whoever is applying it, based on real, observed duplication or drift, not on speculation." This is a process precondition (has duplication actually been observed?), not a structural one the catalog can check mechanically — nothing in `depends_on`/`built_on_plateau` could encode it — so it stays in prose, exactly as in the [v3 map](skills/dotnet/architecture/v3/variability-map.md).

### VP8's constraint (satisfied by construction in this family)

In [v3](skills/dotnet/architecture/v3/variability-map.md), `HttpApi=Yes` required `(CommandIntegration=Yes OR QueryIntegration=Yes)` — see [[skills/dotnet/architecture/v3/plateau/plateau-service-with-api/adr/require-at-least-one-mediatr-source.md|that ADR]]. In v3.1 the Feature Model makes `MediatorModuleIntegration` (Command + Query dispatch) a **common** feature, so `solution-http-api-publication`'s `depends_on` on `solution-query-integration` + `solution-command-integration` is always satisfied. The constraint is kept in mind but is inert unless a future variant ever removes MediatR dispatch from the common baseline (e.g. a pure pass-through proxy module).

## Grouping features and selectors that are not VPs

Following the Feature Model's own "deliberately not rows" note and [[skills/common-workflow/architecture/design/plateau-map/variability-map-create.skill/variability-map-create.skill.md|variability-map-create]]'s Or-group rule:

- **`SyncInboundApi` / `SyncOutboundApi`** — umbrella features, each an `Optional (at least one)` parent of two independently-optional transports. They get no VP row of their own: `SyncInboundApi` ≡ `(VP8=Yes OR VP9=Yes)` and `SyncOutboundApi` ≡ `(VP10=Yes OR VP11=Yes)`. The "at least one" is the statement that you cannot select the umbrella without a transport — but since neither transport requires the other, they are two boolean VPs, never enumerated combinations.
- **`AsyncInboundApi` / `AsyncOutboundApi`** — kept **as** VPs (VP12, VP13) because each is 1:1 with a single `Mandatory` realization (`KafkaConsumer`, `KafkaProducer`), not an "at least one of N" group.
- **Entity classification** (Internal/External × Immutable/Mutable) — the per-entity *selector* that decides which of VP5/VP6/VP7 apply. It has no independent Yes/No, so it is not a VP; it appears only in the **Realization depends on** column of VP5–VP7. Realized by [[skills/dotnet/architecture/v3/solutions/solution-entity-classification.skill/solution-entity-classification.skill.md\|solution-entity-classification]].
- **Cecil architecture tests** — a mandatory companion of VP4, never applied independently. Not a VP; folded into VP4's **Realized by**.

### Combinations the family now allows that v3 has no plateau for

The Feature Model adds axes v3 never modelled — **VP10–VP14 (outbound sync + async messaging)** are entirely new and aspirational, so any plateau touching them is future work once their solutions exist. Within the axes v3 already had, the [v3 map's open combination](skills/dotnet/architecture/v3/variability-map.md#Plateau Map derivation) still stands: `VP2=Yes` + `(VP8 or VP9)` + `VP4=No` — a persisted module with an external API but no centralized rules — has no dedicated plateau, because `plateau-v1` always brings `VP4=Yes`.

## Out of scope

- **Realized-by points into `v3/`, not `v3.1/`.** v3.1 has no `solutions/` of its own yet; when it grows them, every **Realized by** cell must be re-pointed and each **aspirational** marker removed once a real solution exists.
- **VP10–VP14 are unrealized.** They come from the Feature Model's intended-Program-Family scope. Their Variants, Constraints, and "Mandatory realization" notes are taken from the Feature Model diagram, not from working solutions — treat them as provisional until authored.
- **Only one cross-tree Constraint is verified** (VP3, and even that is flagged as not yet encoded in a `depends_on`). VP5–VP7's `requires VP2` is backed by real `depends_on` edges in the v3 entity solutions; VP14's `requires VP13 AND VP2` is Feature-Model reasoning only. The absence of other Constraints reflects this pass, not a proof.
- **Migration is `No` everywhere** — no case in this family has yet been observed changing a VP answer after a module was already composed. Per the parent skill, `Migration` is set `Yes` only on a real observed transition, never speculatively.
- **Plateau Map derivation is empty by design** — `v3.1/plateau/` does not exist. The reference table maps *v3's* plateaus onto v3.1's VPs to show the shape; it is not a claim that those plateaus exist in `v3.1/`.
- **Entity-level VPs (VP5–VP7) are answered per persisted entity**, not once per module — the only rows in this map at that granularity, matching the Feature Model's mixed-granularity note.
