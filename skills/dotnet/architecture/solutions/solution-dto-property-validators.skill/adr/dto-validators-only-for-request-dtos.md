# Problem

The solution requires a validator for every public DTO. In a command-based architecture the system receives a request, validates it, executes the command, and returns a response. The response is built by the application itself, so it is already considered correct. Validating outgoing responses therefore adds code that is rarely executed and creates maintenance overhead.

At the same time, removing the rule entirely would leave gaps for incoming request validation. We needed a clear boundary: which DTOs must have validators and which ones are optional.

# Selected variant

**Selected variant:** [[#Create validators only for RequestDto by default]]

Create a `{Dto}Validator` in `/{Module}.Application/Validators/Model` extending `AbstractValidator<{Dto}>` for every **RequestDto** published in `{Module}.Interfaces`.

Do **not** create a validator for **ResponseDto** unless there is an explicit requirement to validate that response, for example:

- the response is published to an external consumer and a contract-level check is mandated;
- the response is built from untrusted data and must be verified before leaving the module;
- a test or integration boundary explicitly requires response validation.

- RequestDto validators participate in the standard validation pipeline (`ValidationBehavior`, `AddValidatorsFromAssembly`).
- ResponseDto is trusted because it is produced by the handler/application logic.
- A ResponseDto validator, when required, is registered and consumed through the same `IValidator<T>` mechanism as any other DTO validator.

# Searched variants

## Create a validator for every public DTO

### Description

Require a `{Dto}Validator` for every DTO in `{Module}.Interfaces`, including RequestDto and ResponseDto.

### Benefits

- Uniform rule that is easy to check.
- Catches accidental corruption of outgoing responses.

### Costs

- Forces validation code for responses that are generated by trusted application logic.
- Adds noise to the codebase and increases maintenance.
- Validation pipeline typically runs only for incoming requests, so ResponseDto validators are rarely used.

## Create validators only for RequestDto by default

### Description

Require a `{Dto}Validator` only for RequestDto. ResponseDto validators are created only when explicitly required.

### Benefits

- Focuses validation where it matters: incoming requests from external consumers.
- Reduces boilerplate for responses produced by trusted handlers.
- Keeps the validation pipeline lean and predictable.
- Aligns with the command pattern where commands are validated before execution.

### Costs

- Developers must distinguish RequestDto from ResponseDto when creating validators.
- A ResponseDto built from invalid internal state is not caught by validation; such issues must be handled by tests or domain invariants.

## Never validate ResponseDto

### Description

Forbid ResponseDto validators entirely.

### Benefits

- Simple rule with no exceptions.

### Costs

- Removes flexibility for cases where response validation is genuinely needed, such as external contract validation or untrusted response sources.
- Could force workarounds that bypass the standard validation infrastructure.
