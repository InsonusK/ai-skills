# Problem

Supporting both light and dark appearance traditionally requires either a second, hand-maintained set of theme values, or a runtime class-toggling mechanism that swaps out CSS custom property values. Angular Material's M3 `mat.theme()` mixin already generates its color variables using the CSS `light-dark()` function tied to the `color-scheme` CSS property, letting the browser itself resolve the correct value based on the user's OS preference (or an explicit override), natively and without JavaScript.

# Selected variant

**Selected variant:** [[#color-scheme + light-dark() (Material's built-in mechanism)]]

Both this design system's own `--ds-*` tokens and Material's `--mat-sys-*` tokens are defined using `light-dark(lightValue, darkValue)`, with `color-scheme` set appropriately (`light dark` to follow the OS preference, or overridden per an explicit user toggle if one is added later).

# Searched variants

## color-scheme + light-dark() (Material's built-in mechanism)

### Description

Every color token — both Material's own and this design system's custom `--ds-*` additions — is defined as `light-dark(lightValue, darkValue)`. The browser natively resolves the correct value based on the `color-scheme` property and the user's OS-level preference, with zero JavaScript involved in the common case (following OS preference).

### Benefits

- Native browser behavior — no runtime class-toggling logic to write or maintain for the common case of following the OS preference
- Directly consistent with how Angular Material's own M3 theme mixin already defines its tokens, so this design system's custom tokens follow the exact same mechanism rather than a parallel, bespoke one
- Nearly free to adopt given the token-consumption strategy already established — defining `--ds-*` tokens with `light-dark()` costs no more than defining them with a single flat value

### Costs

- Requires a reasonably modern browser baseline (widely supported at this point, but still a dependency on the `light-dark()` CSS function's availability)
- An explicit, user-triggered light/dark toggle (as opposed to following OS preference) requires a small amount of additional plumbing (setting `color-scheme` explicitly rather than `light dark`), though this is a modest addition on top of the mechanism itself

## Hand-maintained parallel dark theme (class-toggling)

### Description

Define a complete second set of theme values under a `.dark-theme` class (or similar), toggled via a JavaScript-added class on the root element.

### Benefits

- Full manual control over exactly when and how the dark variant activates
- Well-understood, long-standing pattern, not dependent on a specific CSS function's browser support

### Costs

- Every token needs a manually maintained light AND dark value defined in two separate places, doubling the surface area for a value to drift or be forgotten when updated
- Requires JavaScript to toggle the class, even for the common case of simply following the OS preference — `light-dark()` provides that for free
- Diverges from how Angular Material's own M3 tokens are already implemented, creating two different dark-mode mechanisms in the same application (Material's own via `light-dark()`, this design system's custom tokens via class-toggling) unless deliberately kept in sync
