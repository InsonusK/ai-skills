### VP3 modifies `solution-repository-structure`

V1 `solution-repository-structure` mandates "every business feature is split into at least a `feature` lib and a `data-access` lib **from the start**". Once `BackendDataAccess` is a VP, a no-backend feature has no `data-access` lib. That solution is modified (a feature is a `feature` lib; `BackendDataAccess` adds the `data-access` lib for features with server data) and the decision recorded as [[skills/angular/architecture/v3.1/solutions/solution-repository-structure.skill/adr/feature-lib-split-conditional-on-backend-data-access.md|a v3.1 ADR]] per [[skills/common-workflow/architecture/design/solution-update.skill/solution-update.skill.md|solution-update]].

### VP2 gates VP4/VP5/VP7/VP8 — the "requires GlobalStore" constraint

`OfflineReadResilience` (`connectivity` slice), `OfflineWriteQueue` (`notifications` slice), `Authentication` (`auth` slice), and `PersistedState` (`preferences` slice) each write a classical NgRx slice, which only exists once `GlobalStore=Yes`. This is the same shape as dotnet v3.1's "VP5/VP6/VP7 require VP2 (Persistence)". Encoded as a `depends_on solution-global-store` edge on `solution-offline-first`, `solution-offline-sync`, `solution-authentication`, and `solution-persisted-state`, and recorded in [[skills/angular/architecture/v3.1/solutions/solution-global-store.skill/adr/stateful-vps-build-on-the-global-store.md|a v3.1 ADR]].

### VP3 gates VP4/VP6/VP7 — the "requires BackendDataAccess" constraint

`OfflineReadResilience` needs a Client to throw `OfflineTransportError` and API GET routes to cache; `BackendLogDelivery` sends batches through `http-core`; `Authentication`'s interceptor, silent-refresh and login are all HTTP round trips. All four realizing solutions carry a `depends_on solution-api-http-layer` edge: `solution-offline-first`, `solution-offline-sync`, and `solution-logging-global` from V1; `solution-authentication` gained it in Stage 3 (a V1 gap).

### VP5's `notifications` slice

`solution-offline-sync` surfaces conflict messages through a `notifications` slice that V1 leaves as a worked-example stub in `solution-state-management` and never actually creates. Resolved (owner, Stage 3 / delta-conflict): `solution-offline-sync` (v3.1) creates it.

## Features that are not VPs

- **The seven common baseline features** — every member of this family includes them; they are shared core, not variability. `SignalForms` and `ConsoleLogging` are common *conventions* (zero cost for an app with no forms / that never logs), a deliberate owner call, mirroring dotnet v3.1's `SoftValueObjects` / `AppLogging`.
- **`ComponentTesting`** — **flagged** (feature-model open question 2): V1 puts it in the first plateau (→ common), first principles say visual/a11y *automation* is a quality gate (→ variable). **Owner's working default: common**, so no VP row — every monolith plateau composes `solution-ui-testing`. A later ruling to variable would make it VP9 (Yes/No, realized by `solution-ui-testing`).
- **The `auth` / `connectivity` / `notifications` slices** — each is a part of VP7 / VP4 / VP5, added to `GlobalStore`, not an independent choice.
- **`solution-ui-testing` was split** (Stage 3 / delta-conflict) — V1's single solution declared `design-system-structure` + `design-system-components` (the `design-system/` catalog). It is now a monolith-side [[skills/angular/architecture/v3.1/solutions/solution-ui-testing.skill/solution-ui-testing.skill.md|solution-ui-testing]] (deps: `repository-structure` + `app-testing` + `forms`) and a design-system-side [[skills/angular/architecture/v3.1/solutions/solution-design-system-ui-testing.skill/solution-design-system-ui-testing.skill.md|solution-design-system-ui-testing]].

## Out of scope

- **`Migration = Yes`** is asserted for VP1/VP4/VP5/VP6/VP7 on the strength of the V1 plateau chain, which documents exactly those transitions as named milestones. dotnet v3.1 marked everything `No` for lack of an observed transition; the Angular V1 chain **is** that evidence.
- **Constraint evidence**: every Constraint is backed by a real `depends_on` edge in the realizing solution. VP4→VP3, VP5→VP4, and VP6→VP3 came from V1; VP2's gating of VP4/VP5/VP7/VP8 was added in Stage 3 and recorded in [[skills/angular/architecture/v3.1/solutions/solution-global-store.skill/adr/stateful-vps-build-on-the-global-store.md|a v3.1 ADR]]; VP3's gating of VP7 is inherent to `solution-authentication`'s HTTP usage (interceptor, silent refresh, login).
- **The plateau↔VP matrix, lineage, and V1 reference mapping** live in [[skills/angular/architecture/v3.1/monolith/plateau/plateau-repository.md|plateau/plateau-repository.md]], not here — this map binds VPs to solutions only ([[skills/common-workflow/architecture/design/plateau-map/variability-map-create.skill/adr/no-plateau-view-in-variability-map.md|ADR: no plateau view in the map]]).
- **`platform-host/`, `embeddable-app/`, `design-system/` are separate catalogs** — federation, session sharing, remotes, and the component library are modeled there.
